# スマホ受付の改善（第1段階）

## 店員の操作

入口は `/admin/visits`。「受付・来店中」画面から操作する。

1. 既存客はお名前・呼び名・会員番号で検索して「来店受付」。受付済みならその旨を表示する。
2. 初めての方は同じ画面でお名前・呼び名を入力し「登録して来店受付」。会員番号はW形式で自動発行。
3. 同名の登録（無効も含む）がある場合は保存を止めて候補を表示する。同じ方なら既存の登録で受付。
   別人と店員が確認した場合に限り、確認欄を選択して新しい会員として登録する。
4. 完了したら「卓に配置する」か「次のお客さんを登録」を選ぶ。
5. 来店中一覧では「退店する」。対局中は従来どおり先に卓を解放する。

紙名簿からの一括取込、LINEショップカードのポイント移行、QR受付は後続作業。
名前の一致は空白・大文字小文字を正規化した完全一致で確認する。読み仮名・表記揺れ・同一人物の自動判定はしない。
無効顧客の再有効化は今回追加しない。管理者が既存情報を確認し、別人として再登録しない。

## 保存の仕組み

- 既存のCustomer/Visitと監査ログを利用し、スキーマ変更・migrationは不要。
- 全スタッフRoleが受付可能。所属店舗はログイン情報から取得する。
- 公開プロフィールは作らず公開設定は初期OFF。
- 店舗行ロックで新規受付同士のコード採番・同名確認を直列化。
- 無効顧客を含めた既存W番号の最大値から採番し、過去番号を使い回さない。
- 旧来の手入力登録との番号衝突はDB一意制約で拒否し、再試行を案内する。
- 顧客作成・来店受付・監査ログを同じトランザクションで保存。失敗時はすべてロールバック。
- 一回の登録画面ごとのUUIDから専用名前空間の顧客IDを生成。同じリクエストの再送は再作成しない。
  退店後に古い送信が再実行されても新しいVisitは作らない。
- 画面入力は制御された状態に保持し、検証エラー時も名前を失わない。
- 既存顧客の受付・退店でも卓画面を再検証し、待機人数の更新へ反映する。

## 検証

- DBに接続しない単体テスト：入力、採番、同名・無効顧客、店舗分離、再送、保存失敗時の取り消し。
- 既存の顧客・来店の回帰テスト、TypeScript、ESLint。
- 実行結果：DB統合テストを除く14ファイル80テスト成功、型チェック・ESLint・本番ビルド成功。
- 実スマホでの受入確認は未実施。登録操作は実データを書き込むため、開発DBのサンプルで確認する。
- 画面確認時に既存Chromeの別資料を露出する恐れがあるとして自動承認レビューがウィンドウ操作を拒否。
  そのウィンドウを操作していない。表示の実確認は未完了。

受入項目：既存客受付／新規登録と受付／同名別人／無効顧客／受付済み／エラー時の名前保持／次の人への連続登録／卓への配置／退店後の再来店。
