## 確定した方針

- LINE非依存の独自会員システム。LINE Login・LINEアカウント連携・LINE APIによるポイント自動移行を作らない。
- 顧客の電話番号・メールアドレスは原則不要。通常のID・パスワードを新たに作らせない。スタッフの既存認証は維持する。
- スタッフが既存客を検索し、未登録なら名前だけで登録する既存の受付を活用する。同名だけで自動統合しない。
- 成績とポイントは、店舗スコープとCustomer内部IDに結び付ける。Cookie削除・機種変更・認証の更新で別会員を作らず、履歴を継続する。
- 本人専用マイページはパスキーを使用する。有効なセッション中はログイン操作を省き、失効時にパスキーで再認証する。パスキーが使えなければ復旧コードを使う。
- 全認証手段を失った場合は厳格な店頭復旧を検討する。**名前・会員番号だけで再連携を認めない。確認材料が不足する場合は保留し、代替の抜け道を作らない。**
- 来店受付、スマホ連携、本人認証、ポイント付与・利用は別処理。スマホなしでも通常の受付・対局・成績記録を続けられる。
- ポイント交換・消費は店員による承認・処理とする。顧客マイページは残高・履歴の閲覧用とする。

## 初回連携の流れ（計画）

店員が既存客を検索 → 未登録なら名前だけで登録・会員番号自動発行 → 対象Customerの「スマホ連携」 → 短時間有効・一回限りの連携QR発行 → 顧客が読取 → 双方の画面の確認番号と対象を照合 → **店員と顧客の双方が確認** → パスキー登録 → サーバーで登録成功を検証 → 復旧コード発行・保管案内 → マイページ利用開始。

- 既存客のスマホ連携のためにCustomerを作り直さない。連携発行権限・対象店舗・既存認証状態をサーバーで確認する。
- QRの読取だけ、または双方の照合だけで認証完了にしない。パスキー登録が失敗・中断した段階でマイページの認証済みセッションを発行しない。
- 概念上は「発行 → 読取側の予約 → 双方確認 → 資格情報登録待ち → 完了」と、取消・期限切れ・失敗を区別する。状態名、データモデル、期限、再開・再発行方法は実装前に設計する。
- 同時読取・先取り・二重送信・再試行を考慮する。完了時のトークン消費、Customerへの資格情報の確定、監査記録に不整合を残さない。
- 写真を盗んだ第三者に先取りされても、正規の照合と双方確認なしで登録を完了できないことを受入条件にする。確認番号の照合が形だけになるUIを避ける。
- 連携成功から来店受付やポイント付与を暗黙に実行しない。

## パスキー・セッション・機種変更（計画）

WebAuthn/FIDO2に基づく、検証実績のあるライブラリを採用する設計とする。今回は選定・導入しない。登録と認証のチャレンジ、有効期限、再利用防止、期待するorigin／RP ID、対象Customerへの対応をサーバーで検証する。

- 正式ドメイン・RP ID・HTTPSの提供方法を本番利用前に確定する。LAN上のHTTPプレビューだけでパスキー本番対応済みとはしない。
- HttpOnly・Secure・SameSite Cookie、セッションの期限・更新・ローテーション・失効、ログアウト・全端末ログアウトを設計する。Cookie属性だけでCSRF／XSS対策が完了した扱いにしない。
- スタッフ認証と顧客認証のCookie、認可、データ取得経路を分離する。保護ページだけでなく、各API・操作でも失効・店舗・本人を検証する。
- 資格情報の追加・削除は本人の再認証を必須にする。複数資格情報の保持、最後の資格情報を削除する場合の扱い、上限は別途決定する。
- 有効なセッションでは閲覧を継続。Cookie削除・期限切れ時はパスキーで再認証。同期済みパスキーが新端末で利用できる場合はそれを使い、既存パスキーが使える場合は新しい資格情報の追加を可能にする。
- パスキーを使えなければ復旧コードへ進む。全手段を失った場合に名前だけの復旧へ切り替えない。
- 紛失時に資格情報・セッションを失効できるようにする。同期パスキーは物理端末単位と一致するとは限らないため、資格情報単位とセッション単位の無効化を分けて設計する。「特定の実端末だけ必ず失効できる」と断定しない。
- 資格情報そのもの、認証レスポンス、認証トークン、QRトークン、復旧コード、セッションCookieをログに残さない。検証に必要な保存データと操作監査を分け、監査には担当・対象・日時・操作結果など必要最小限の項目を用いる。

## 復旧と連携解除（計画）

初回連携時に十分にランダムな復旧コードを発行し、安全な保管を案内する。提示・保管の具体的方法は未確定。サーバーは原則として検証用ハッシュのみを保持し、平文を再表示できる仕組みを前提にしない。

復旧コードの検証 → 一回限りの消費 → 新しい認証手段・復旧コードの設定 → 必要な既存資格情報・セッションの失効 → 監査記録、を一連の復旧フローとして設計する。設定途中の権限は復旧に必要な範囲に限定し、完了前に通常の本人専用データ閲覧を開放しない。

試行回数制限・総当たり対策・並行利用防止を設ける。盗まれた復旧コードも乗っ取りに使われ得るため、再発行、本人への案内、既存セッション失効・通知方法を決めてから公開する。電話・メール通知を当然に使えるとはしない。

全認証手段喪失時の店頭復旧は、確認資料・権限・承認・保留・監査の方針決定まで実装保留。十分な確認ができなければ再連携しない。連携解除でもCustomer・過去の成績・ポイントを削除せず、認証の失効と会員データの保持を分ける。

## 受付QRとの分離（計画）

店内共通の受付QRは来店手続きへの入口とし、特定会員の認証を行う一回限りの連携QRと別にする。

- 受付QRを持っているだけで非公開成績の閲覧やポイントの利用を許可しない。既存顧客の会員番号を入力するだけで本人と判断しない。
- 認証済み顧客の来店申請、未連携客・新規客の店員案内、店外受付防止、二重受付防止、店員承認の要否を設計する。具体的な承認方法は未決定。
- 新規登録導線は店員検索・確認を基本とする。共通QRから既存客を無確認で複製したり、自動で既存客に連携したりしない。
- スマホなし・非対応端末は店員の既存受付を利用できる。本人専用Web閲覧の代替認証方式は未確定のまま残す。

## 既存客・ポイント移行・独自ポイントの統合

紙名簿の整理・既存Customerの照合、LINEショップカード残高の移行、独自付与ルール、本人認証は別タスクにする。認証開始や新端末への連携をポイント移行の再実行条件にしない。

- 店員が旧LINEショップカードを目視確認し、正しい既存Customerへ移す。LINE API自動取込は前提にしない。同名客の自動統合は禁止。
- 移行日・担当者・移行ポイント数・移行元・確認根拠を記録する。根拠の保存方法・保存範囲は未確定で、不要な第三者の個人情報を取り込まない。
- 同じ旧残高を別端末・別Customer・再送から重複移行しないため、移行元の照合方法、対象単位、再実行制限を設計する。「Customer一人一回」だけで十分と判断しない。
- 旧カードの付与・利用を止める切替日と手順、移行中の扱い、確認・承認、誤移行時の訂正手順を決める。切替で旧・新双方の二重付与や二重消費を発生させない。
- 残高だけでなく、付与・使用・訂正・移行の台帳を保持する。二重実行防止と残高・台帳・監査の整合性を確認する。
- 予定する付与ルール：来店1pt、連続来店追加1pt、同一営業日の5ゲームごと1pt（10ゲームなら2pt）、1位1回ごと1pt、役満は店員記録1回5pt。再来店の重複扱い・定休日を挟む連続来店などの未確定条件は決めてから実装する。
- 対局訂正に伴うポイントの補正、店員による交換・消費・取消・理由付き調整を設計する。顧客用APIで消費させない。具体的なスタッフ権限差は未確定。
- ゲーム代バックは現金交付しサービス料支出として記録する既存計画を維持。付与台帳と支出は別の記録として関係付ける。
- スタッフは当面、顧客向けランキング・特典ポイント対象外という暫定方針を維持する。将来変更する場合の適用日は別途確認する。
- 顧客マイページは、ポイント機能ができてから残高・履歴を追加する。未移行を「残高0」で確定したように見せない。認証の更新や端末変更で台帳を作り直さない。

| P03 旧LINE残高の手動移行・切替 | P2 | C01・P01。確認・承認・切替を決定 | 正しいCustomerに移行日・担当・移行ポイント数・移行元・根拠を保存。旧カードの付与／利用停止と二重移行防止を運用できる | 同名誤移行・別Customerへの再移行・再送・旧新二重利用・訂正（T13・T14・T16） |
| P04 店員による交換・消費・調整 | P2 | P01。特典・権限・取消・現金バックを決定 | 店員のみ承認・処理し、残高・台帳・監査を整合させる。顧客向け読取APIに消費権限を持たせない | 権限不足・二重消費・残高不足・取消・現金バック整合（T14・T18・T19） |
| P05 マイページのポイント閲覧 | P2 | M01・P01、利用者の移行状態はP03に従う | 本人の残高・履歴と未移行状態を表示し、端末変更後も同じ台帳を参照。交換は店員へ案内 | 別人・別店舗・再認証後の継続・未移行表示（T01・T12・T15・T16） |
| S01 認証・公開・ポイントの安全性受入 | P1・各公開前必須 | 対象機能の実装と決定事項。実装と並行して検証を設計 | 下記テストを該当機能の公開前に通し、未確認・不合格のまま公開しない。実機で登録・再認証・復旧を確認 | T01〜T22。公開する範囲に必要な全項目 |

依存は機能ごとに適用する。M01の成績だけの公開にポイント完成を要求しない。R01の匿名閲覧に顧客ログインを要求しない。ただし各々の本人認可・公開同意検証は省略しない。C08の運用が未決定の間は店頭復旧を提供せず、C06による安全な復旧と「全手段喪失は保留」の案内を用意する。

## 推奨する進め方

1. B00：既存の店員操作の実スマホ通し確認を終える。途中のスタッフ参加タスクの検証・保存は別指示の範囲で扱う。
2. C01・C02：既存Customerの照合と認証の設計を確定。P01の台帳設計は認証とは独立して整理できる。
3. C03 → C04 → C05 → C06 → C07：連携・パスキー・セッション・復旧・機種変更を整え、S01の関連検証を通す。
4. Q01・M01・R01：依存に沿って受付QR・本人の成績・同意制の公開ランキングを別々に追加する。公開プロフィール詳細と対戦相手履歴は未決定のまま実装しない。
5. P01 → P02／P03／P04 → P05：独自ポイントを整え、切替手順に沿って旧残高を移し、本人用閲覧を追加する。P03の移行とP02の新規付与を同じ処理にしない。
6. C08：具体的な確認・許可条件を合意できた場合に限り、店頭復旧を追加する。各段階でS01を実施し、関係する未確認・不合格があれば公開しない。

初回の計画更新では製品コード・Prisma・DB・アカウント・環境変数を変更せず、Git commit／push、有料契約も行っていない。その後の実装は追加指示に基づきタスク単位で確認・ローカルコミットする。push・本番公開・有料契約は別指示とする。上の検証項目は実施結果を別途記録するまで動作確認済みと表示しない。
