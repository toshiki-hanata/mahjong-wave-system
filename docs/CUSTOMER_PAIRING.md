# 初回スマホ連携QR・双方確認（2026-10-31）

C03として初回連携の発行・読取・双方確認・取消を実装。パスキー登録（C04）・顧客セッション（C05）・復旧（C06／C07）・本人マイページはまだ未実装。双方確認だけでは認証完了にしない。

## 操作

1. 店員は既存の会員を検索し、顧客詳細の「この会員のスマホ連携へ」→ `/admin/customers/[id]/link`を開く。既存会員を新しく作り直さない。
2. 対象を確認して「新しい連携QRを発行」。開発仮設定では5分で期限切れ。再発行すると前の未完了QRは無効になる。
3. 顧客がQRを自分の端末で読む。`/member/link`に確認番号を表示し、店員の画面でも同じ番号を確認する。
4. 顧客が「店員と番号が一致し、自分の会員であること」を確認。店員も表示中の対象会員と顧客の画面を照合して確認する。どちらが先でも、両方が必要。
5. この段階は資格情報登録の準備完了。まだ初回連携・ログイン完了にはしない。パスキー登録は後続C04で追加する。
6. 対象や読取端末が違う、期限切れ等の場合は取消・再発行。取消後や期限切れ後は古いQR画像を隠し、顧客画面でも無効を表示する。

現在はlocalhostの開発設定。本物のスマホでパスキーを使う前に、HTTPSと正式な認証アドレスを準備して再確認する。LAN上のHTTPで見る従来の受付画面と、パスキー対応は別。

## 境界

- QRには推測困難な256bitトークンを使い、DBへはSHA-256ハッシュだけを保存。トークンはURLのクエリーやパスに置かずフラグメントで渡し、読取後にURLから除去する。Cookie設定後の画面応答で元URLが戻る事象も検証・修正した。
- 画面の確認番号は照合用で、番号を入力して認証するAPIは設けない。顧客側では内部Customer ID・店舗ID・内部管理名を返さない。
- 読取ブラウザーは別のランダムトークンをHttpOnly・SameSite=Strict・期限付きCookieに保持する。HTTPSならSecure。Cookieは/memberだけで使い、スタッフCookieと分ける。サーバーで期待originも検証する。
- QRの先着読取だけで会員の認証を確定しない。別端末への読取差替えは拒否し、誤った先取りは店員が取消・再発行する。異なる端末からの再読取失敗が5回に達したQRは無効にする。発行はスタッフあたり1分10件まで。
- 店舗→連携行のロックで発行・再発行・確認・取消を直列化。未完了の有効候補は会員あたり1行という部分一意索引でも守る。期限の判定はサーバーを基準にする。
- 各スタッフ操作は認証済み店舗・現スタッフの有効状態を使う。表示中のCustomerと連携IDの両方を照合し、別会員のフォームからの確認・取消を拒否する。
- 一度パスキー登録を完了した会員は初回QRを発行できない。全認証手段喪失時の未確定な店頭復旧を、このQRで代替しない。顧客データと認証の再連携を分ける。
- 来店・対局・ポイント・認証済み顧客セッションは発行しない。監査は発行・読取・双方確認・取消・失敗上限を記録し、QR／Cookieの秘密値や確認番号は出さない。
- 既存の店員受付、スタッフログイン、公開同意は変更しない。
