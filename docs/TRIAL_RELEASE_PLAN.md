更新：2026-11-20。開始13:50 JST、目標19:50ごろ。6時間は目標であり公開の保証ではない。

## 最小の対象

スタッフログイン → 営業開始 → 架空客の受付 → 卓配置/交代 → 半荘入力/訂正 → 卓終了/退店 → 本数・売上・成績 → 営業終了。

顧客マイページ/パスキー、LINE移行、自動ポイント/交換、セット予約、未完成の顧客連携を公開対象へ追加しない。未完成機能の既存hosted遮断を維持する。

## 6時間内の進め方（目安）

| 順番 | 作業 | 完了条件 |
| --- | --- | --- |
| 最初の1時間 | プラン/アクセス権/試運用専用DB・公開先を確定 | 課金の承認と対象環境が明確。既存環境へ影響しない |
| 次の2時間 | 架空データと試運用用の最小権限、公開構成を用意 | 新規の空環境のみ。実客・既存Staffのコピーなし。認証・DB権限・環境分離の確認成功 |
| 次の2時間 | 制限付きHTTPSでPCとスマホ確認 | 匿名・対象外アカウント拒否、MFA、受付から営業終了、訂正、再送/競合、通信断を確認 |
| 最後の1時間 | 見つかった問題の修正・再検証と利用開始判断 | 重大な未解決問題なし。利用者・URL・手順・制限・停止方法を記録 |

## 試運用URLを共有する前の条件

1. 対象サービスの利用条件と費用を確認し、必要な有料操作は本人が承認する。
2. 既存のDBへ接続せず、架空データだけの専用環境を使う。本番用のSecretを流用しない。
3. アプリの最小権限DB Roleを実際に確認する。owner資格情報をVercelに置かない。
4. Vercel Authentication等の制限をURL全体へ適用し、匿名で拒否されることを確認する。「URLを知る人だけ」を保護にしない。無料Viewer等を使い、有料席を勝手に追加しない。
5. アプリ側でもOWNER/MANAGERにMFAを要求する。パスワードだけの解除・本番停止ガードの迂回を行わない。本人が初回登録と復旧コード保管を確認する。
6. 試運用であることと「実際のお客さんの情報を入力しない」を利用者へ明示する。
7. 正式な試運用OriginとHTTPSでCookie・CSRF・ログアウト・期限を確認する。WebKitのローカルHTTPでのSameSiteメタデータ差は実Safari/HTTPSで再確認する。
8. 専用の架空客で営業の通し操作・訂正・通信断・二重送信を確認。実iPhone/Androidで未確認の範囲を明記する。
9. 利用を止める方法とテストデータの扱いを記録する。試運用を本番の復元試験完了とは扱わない。

未達なら、公開を強行せずローカルでの操作確認までに留める。本番利用のNo-Go条件は[公開・復旧手順](SECURITY_RELEASE_RUNBOOK.md)のまま。実客データを使う場合は、本番DB・バックアップ復元・外部設定・実機営業受入を改めて満たす。
