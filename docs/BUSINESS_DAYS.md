# 営業開始・終了（第2段階）

## 店員の操作

入口 `/admin/business-days`。メニューの「営業開始・終了」と全管理画面上部から開ける。

1. 「営業を開始する」。スタッフ3権限とも操作可能。番責の割当は後続作業。
2. 受付→卓開始→半荘結果を登録。開始時点の店舗タイムゾーン・単価を営業に保存する。
3. 0時を過ぎても自動終了しない。受付・対局は明示的に開始した同じ営業へ紐付ける。
4. 終了前に最後の半荘結果を保存→卓解放→全員を退店。
5. 営業画面で本数・売上を確認し、確認欄にチェックして営業終了。

営業していない間は新規受付・卓開始・新しい対局結果の登録を拒否する。
既存の卓解放・退店は営業開始前でも可能。以前の未処理データがある場合は先に片付ける。
未入力の半荘自体は自動検出できないため、終了確認欄で店員が確認する。

## 売上・履歴

- フリー1本＝1卓で半荘が1回終了して結果確定。4人分を4本と数えない。
- 初期単価2,500円。OWNER/MANAGERが次回営業からの料金を変更可能。
- 営業開始時と各Gameに単価を保持。営業中に設定を変更しても当該営業・過去の金額は変更しない。
- 有効なCONFIRMEDだけを集計。訂正版は同じ営業ID・単価・集計時刻を引き継ぐ。
- 終了後の点数訂正も可能。本数と料金は変わらず、元の結果と監査ログを保持。
- 売上はゲーム代バック・経費を引く前の金額。現金残高・収支・サービス料はまだ含めない。
- 営業別・卓別の本数／売上、来店実人数、再来店込み受付回数、最近10営業の履歴を表示。
- 営業名の日付は開始時の現地暦日。暦日が同じでも別々に開始・終了した営業は別IDで保持。
- 既存の月間・年間ランキングは従来の店舗タイムゾーンの暦月・暦年のまま。

## DB・同時操作

- 20261029090000_business_days と 20261029091000_business_day_close_constraint は追加中心の変更。
  旧Visit/TableSession/Gameの営業ID・単価はNULLで残し、推測で過去営業へ割り当てない。
- 店舗内で同時に開ける営業は1件（DB部分一意インデックス）。
- 店舗を最初にロックし、営業開始・終了と受付・卓・対局・顧客更新を直列化。
- 営業終了時は店舗内すべての未退店・稼働卓を再確認。同時操作で受付が滑り込むことを防ぐ。
- 開始リクエストキーと終了対象IDで再送を識別。古い開始リクエストで閉じた営業を再開しない。
- 開始／終了／料金設定は監査ログに保存。店舗IDを含む複合外部キーで他店舗との混在を防止。
- スキーマ適用前後の既存レコード件数は別途確認。reset・seed再実行・削除は行っていない。

## 検証と残件

- 単体テスト：深夜・タイムゾーン、再送、開いたままの営業、旧営業への終了再送、未退店・卓の終了防止、店舗分離、価格履歴、監査失敗のロールバック。
- DB統合：RUN_BUSINESS_DAY_DB_TESTS=true と既存のDB安全ゲートを必須とする。
  独立した検証用店舗を外側のトランザクション内に作り、受付→対局→訂正→退店→終了→次営業まで確認し、全変更をロールバックする。
- 旧来のVisit/Table/GameのDB統合テストは、専用開発DBで営業開始済みの状態が前提。
  テスト対象外店舗を自動開始しない。今回それらの永続化型の既存DBテストは実行していない。
- PC上の隔離したヘッドレスChromeで390px・430px幅の営業・受付・卓画面を表示し、横スクロールとJSエラーを確認。
  店員のセッションはテスト用にメモリ上だけで作成し、Cookie・秘密値・ブラウザープロフィールを保存／共有しない。
- 実スマホのタップ感・キーボード操作は店舗での確認が必要。
- 単体89件、営業日専用のロールバックDB統合1件、型チェック・ESLint・本番ビルドが成功。
  390px／430pxの3画面で横はみ出し・JSエラーなし、メニューから営業画面への移動・7卓表示を確認。
- Windowsでは起動中のPrisma DLLがロックされることがある。今回はgenerateを済ませた状態で`npx next build`を実行して本番ビルドを検証した。
- 再開・終了忘れの外部通知、セット／予約／スタッフ対局の営業連携は未実装。時刻訂正・終了忘れの処理は下記のとおり追加済み。

## 営業日時の訂正・終了忘れ（2026-10-30追加）

ユーザー確認済みの運用：OWNER／MANAGER限定、実際の終了日時を指定、理由・担当者・変更前後を履歴保存。未退店・利用中の卓がある場合は先に整理する。

- 営業中の「営業終了前の確認」→「営業終了を押し忘れた場合」で実際の終了日時を入力して締める。
- 最近10営業の履歴で「開始時刻を訂正」または「開始・終了時刻を訂正」を開く。
- 日付をまたいで営業中の場合は終了忘れの確認文を表示。自動終了や強制退店は行わない。
- 画面の日時は営業開始時に保存した店舗タイムゾーンで解釈。端末・サーバーのタイムゾーンには依存しない。
- 理由と確認欄が必須。入力エラー時は日時・理由を保持する。
- 開始・終了の順序、未来の日時、別営業との時間の重複、紐付いた来店／退店・卓開始／終了・対局時刻との矛盾を拒否する。
  退店・卓終了の操作も後日行った場合、その記録より前には締められない。記録自体を推測で書き換えない。
- 終了後の点数訂正は元のeffectiveAtを基準に判断し、訂正を登録した日時を営業の終了時刻に要求しない。
- 開始日の訂正では営業名の日付を再計算。営業ID・来店／対局の所属・記録時刻・料金・単価は変更しない。
- 終了済み営業の再開は提供しない。元の終了担当者は残し、訂正担当者は監査ログに別途記録する。
- Server Actionとサービスの両方で権限確認。店舗ロック、送信時の開始／終了時刻との照合、リクエストキーで上書き競合と二重送信を防止。
- 変更と監査ログは同一トランザクション。履歴では日時・担当・理由と変更前後をOWNER／MANAGERが確認できる。
- スキーマ変更・migrationは不要。

## 店舗ホーム（2026-10-30追加）

- 管理トップ `/admin` の表示を自店舗の実データへ切替。旧デモの売上グラフ・飲食売上・目標・前日比などは営業トップには表示しない。
- 今回の営業のフリー本数・売上・来店実人数、現在の待機／対局中人数、有効卓と現在の参加者、確定結果の直近5件を表示。
- 集計は営業IDとCONFIRMEDに限定。日付が変わっても同じ営業。訂正前や前営業の結果を二重計上しない。
- 営業していない場合の本数／売上は「—」。実際に営業中で0件の場合と区別する。
- 受付・退店／卓・結果入力／営業開始終了／顧客名簿／ランキングを実画面へのリンクにする。
- 旧デモのソース・見本素材は保持。顧客別会計・飲食売上を新たに実装していない。
- 読み取りはRepeatableReadの同一スナップショット。顧客情報はスタッフ認証後の管理画面でのみ表示する。

### 今回の検証

- 単体119件、時刻訂正と一日営業のロールバックDBテスト2件、型チェック・ESLint・本番ビルド。
- DBテストは既存の安全ゲート必須。独立した検証店舗内で時刻訂正・権限・重複・履歴・失敗時の取り消しを検証し、全変更をロールバックする。
- ホームの集計は結果訂正・メンバー交代・次営業への切替を含む実DBテストで確認する。

- 起動中の管理ホーム／営業画面も390px／430pxで読み取り確認し、横はみ出し・JSエラーなし。ホームの卓数はDBの有効卓数と一致し、業務リンクが実画面を指すことを確認。

スマホで見る場合はPCと同じWi-Fiで `http://<PCのLANアドレス>:3000/admin/business-days`。
